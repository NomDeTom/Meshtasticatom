# One required dependency, two optional ones.
#
# PyYAML is required for any run that loads a packaged scenario - `--scenario batumi` reads
# presets/batumi.yaml, and terrain.py imports yaml lazily inside preset_scenario(), so a flat or
# landform run never touches it and an environment without PyYAML looks fine until the first real
# geometry. This file said "nothing installed at all" until CI proved otherwise: the transport suite
# passed on a developer machine with PyYAML as a system package and failed on a clean runner with
# three errors, all on the preset path.
#
# Seven of the ten vendored modules SF++ imports are pure standard library: lib.clutter,
# lib.config, lib.link_model, lib.phy, lib.radio_loss, lib.srtm, lib.terrain.
#
# The other three are not, and this list said they were. lib.presets was missing from it entirely,
# and lib.map_input and lib.osm_clutter were named as clean. Each reaches numpy, pandas and simpy
# transitively - simpy through lib.node, numpy through lib.common and lib.point, pandas through
# lib.discrete_event - so anything under the scenario path needs the root requirements.txt, not just
# PyYAML. That is the same shape of gap PyYAML was: CI caught the yaml import because it is named in
# a module SF++ calls directly, and did not catch these because they are two hops away.
PyYAML>=6.0

# Optional, and neither is needed for a scheduled run. The charts a run draws for itself are SVG
# written by autochart.py with no dependency at all, so CI gets them; matplotlib is only for the
# hand-run figure tools. The test gate falls back to unittest when pytest is absent.
matplotlib>=3.5   # the hand-run figure tools: figures.py, figures3.py, diagram.py,
                  # knowledge.render(). The charts a run draws for itself are SVG written by
                  # autochart.py with no dependency, so an unattended run gets them too.
pytest>=7         # nicer test runner; unittest runs the same suite

# under sfpp/ uses it" was true of the tooling and false of the dependencies.
